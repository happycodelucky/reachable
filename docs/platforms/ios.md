# iOS

Reachable's iOS implementation wraps Apple's Network framework
`nw_path_monitor` C API via Kotlin/Native cinterop. The same code path
covers iPadOS and macOS — both Apple platforms share the `appleMain`
source set in `:reachable`.

## Construction

```swift
import Reachable

let reachability: any Reachability = Reachability()
```

`Reachability()` is a top-level Swift function generated by SKIE from the
top-level Kotlin factory `fun Reachability(): Reachability` in
`appleMain/Reachability.apple.kt`. The construction:

1. Creates a per-instance serial dispatch queue:
   `dispatch_queue_create("dev.reachable.monitor", null)`.
2. Calls `nw_path_monitor_create()` to get the monitor handle.
3. Registers an update handler that maps each `nw_path_t` to a
   `ReachabilityStatus` and pushes it through `MutableStateFlow.value`.
4. Calls `nw_path_monitor_start(monitor)`.

The first emission lands on the dispatch queue typically within tens of
milliseconds. Until then, `status.value` returns
`ReachabilityStatus.Unknown` from the base class.

## What gets read

For each `nw_path_t` the update handler receives:

| Reachable field        | Cinterop call                                                       |
|------------------------|---------------------------------------------------------------------|
| `reachable`            | `nw_path_get_status(path) == nw_path_status_satisfied`              |
| `transport.Wifi`       | `nw_path_uses_interface_type(path, nw_interface_type_wifi)`         |
| `transport.Cellular`   | `nw_path_uses_interface_type(path, nw_interface_type_cellular)`     |
| `transport.Ethernet`   | (always `false` — see [Wired Ethernet limitation](../concepts/validated-vs-available.md#wired-ethernet-on-macos-known-limitation)) |
| `transport.Other`      | `nw_path_uses_interface_type(path, nw_interface_type_other)`        |
| `metering.Metered`     | `nw_path_is_expensive(path)` — cellular or hotspot                  |
| `metering.Constrained` | `nw_path_is_constrained(path)` — Low Data Mode active               |

The `Constrained` signal is Apple-only — Android has no direct equivalent.
See [Concepts → API design](../concepts/api-design.md#meteringconstrained-is-apple-only)
for the rationale.

## Threading

The update handler fires on the per-instance serial dispatch queue. The
handler body just calls `MutableStateFlow.value = ...`, which is
concurrency-safe and thread-aware:

```kotlin
nw_path_monitor_set_update_handler(m) { path ->
    path?.let { p -> emit(toStatus(p)) }
}
```

Collectors observe on whatever dispatcher they collect on. From SwiftUI:

```swift
@MainActor
final class ConnectivityModel: ObservableObject {
    @Published var status: ReachabilityStatus = ReachabilityStatus.companion.Unknown
    private var task: Task<Void, Never>?

    init(reachability: any Reachability) {
        task = Task { [weak self] in
            for await s in reachability.status { self?.status = s }
        }
    }
}
```

The `Task { … }` runs on the global concurrency executor; assignments to
`@Published` happen on the `@MainActor` because of the actor annotation,
so SwiftUI updates are always on the main thread.

## Memory

`nw_path_monitor_t` is reference-counted via the Objective-C runtime
integration. Kotlin/Native's GC manages the handle lifetime; explicit
`nw_release` is **not** required. The library calls `nw_path_monitor_cancel`
in `close()` to tear down the monitor synchronously before the GC reclaims
it.

The dispatch queue is similarly ARC-managed. No explicit cleanup needed
beyond `cancel()`.

## Deployment target

`iOS 18.0` — set in `gradle/libs.versions.toml` and baked into the SwiftPackage
manifest. The Network framework itself is available on iOS 12+ / macOS 10.14+,
so the floor is well above what Apple requires; the iOS 18 pin reflects the
project's broader baseline rather than an `nw_path_monitor` constraint.

If you need a lower floor, fork and bump the deployment target down — the
implementation will keep working on anything iOS 12+.
